# PP-Claw（皮皮虾）：从 0 到 1 实现微信养虾

有一阵子我一直在想一件事：皮皮虾已经能跑 Agent、能接工具、能做定时任务，为什么不能直接住进微信里？

真正把这件事做起来以后，我才发现，难点根本不在模型，也不在 Prompt，而在“通道”这两个字上。个人微信接入，和我们平时理解的“接个 webhook”完全不是一回事。过去很长一段时间里，微信并不是大多数 AI Agent 项目会优先选择的首发渠道。不是因为大家不想接，而是因为对独立开发者来说，缺少一条足够清晰、稳定、可自助落地的个人微信工程路径。现在情况开始变了。随着微信侧出现面向 ClawBot 这类能力的公开说明，个人微信终于不再只是“能不能想办法连上”的问题，而开始变成“能不能把它工程化做好”的问题。

也正因为背景变了，这篇文章就不能再用一句“微信以前没有开放方式”草草带过。更准确的说法应该是：过去，个人微信对大多数开发者并不是一条容易进入、容易维护、容易规模化的公开接入路径；现在，随着新的说明和配套方式出现，这条路终于有了可以认真做产品和工程设计的基础。

这篇文章想讲的，就是皮皮虾是怎么把这条链路真正跑通的。不是写“接微信很简单”的鸡汤，也不是贴一堆零散代码，而是把这次改造背后的思路、参考来源、实现路径，老老实实讲清楚。读完以后，你应该能明白两件事：第一，为什么这件事必须这样做；第二，为什么现在皮皮虾已经具备了微信收发消息的完整能力。

---

## 1. 为什么要做“微信养虾”

所谓“微信养虾”，说白了就是让皮皮虾这个 Agent，直接以个人微信号的形态活起来。你在微信里给它发一句话，它能收到；它思考完以后，直接把结果发回微信，不需要再切到 Web 页面，不需要再开终端，也不需要专门维护另一个聊天入口。

如果把时间往前拨一点，你会发现不少 AI Agent 项目的首发渠道其实不是微信，而是飞书、Slack、Discord 这类平台。原因不复杂，飞书这类渠道对工程团队太友好了：开放平台清楚，文档完整，事件回调稳定，机器人模型成熟，调试链路也顺手。你今天想做一个“能收消息、能回消息、能带权限”的内部 Agent，飞书几乎天然就是一条低阻力路径。

它的优点很明显。第一，接入标准，平台边界清楚，开发者知道什么能做、什么不能做。第二，Webhook 和 Bot API 足够稳定，接进现有服务很顺。第三，企业场景天然成立，权限和组织结构也容易对齐。缺点也同样明显：飞书更像“工作入口”，不是每个人每天最自然的生活入口；它适合把 Agent 带进组织，不一定适合把 Agent 带进个人日常。

微信恰好反过来。它是中文用户最自然的消息入口，触达频率高，真正“有人味儿”的助手体验往往要到这里才成立。但它以前最大的问题，不是价值不够，而是工程路径不够明确。很多团队不是不想做微信，而是不愿意让整个系统建立在一条模糊、脆弱、难维护的通道之上。

我之所以坚持做“个人微信”，而不是先做公众号，原因其实很现实。公众号当然更正规，但它更适合“产品对外服务”；个人微信更适合“我先用起来”。很多人接 AI 的第一需求，不是做一个公开 SaaS，而是希望自己的助手真的能跟着自己生活，能在最熟悉的消息入口里说话。对中文用户来说，这个入口往往就是微信。

而今天重新做这件事，前提已经不同了。既然微信侧已经给出了更明确的 ClawBot 方向和配套说明，那我们讨论的重点就不该停留在“能不能接”，而应该进入下一层：怎样把它做成一个低耦合、高内聚、能长期运行的正式 channel。

---

## 2. 先说结论：个人微信接入，难点不在 AI，在通道

如果只看表面，很多人会以为这件事不过是“收一条微信消息，然后把回复发回去”。真正动手以后才知道，中间至少有五道坎。

第一道坎是登录。个人微信不是平台机器人账号，必须扫码授权，而且登录状态还得保存下来，不然每次重启都要重新扫。

第二道坎是收消息。这里不是 webhook，而是长轮询。也就是说，程序不是在“等微信推给我”，而是主动不断去问“你有没有新消息”。

第三道坎是回复关联。个人微信这条链路里，单纯靠 `chat_id` 不够，真正关键的是一个叫 `context_token` 的字段。这个 token 是入站消息带过来的，回复时必须原样带回去，否则上下文就断了。

第四道坎是媒体。图片、文件、视频都不是直接丢一个 URL 就完事，而是要走 CDN，再加上 AES-128-ECB 加密和解密。这个环节如果不封装好，很快就会把整个项目结构搅乱。

第五道坎是多账号。只要开始认真做个人微信，你就很难永远只用一个号。架构如果从一开始不考虑 `channel + account + chat` 这三个维度，后面一定会串线。

所以这次改造的真正目标，从来不是“加个微信功能”，而是把皮皮虾升级成一个能托管复杂通道运行时的系统。微信只是第一个最难的考题。

这也是为什么我在这次背景重写里，特意把“飞书为什么常见、微信为什么现在才值得重做”放到前面讲。它不是选型趣味问题，而是工程约束问题。飞书的优势在于标准化和低摩擦，适合快速交付；微信的优势在于真实触达和使用频率，适合把 Agent 真正带进生活。现在微信通道有了更明确的落地方向，PP-Claw 才有必要认真补上这块短板。

## 3. PP-Claw 原本的架构，为什么适合接微信

这次能做成，和皮皮虾原本的结构关系很大。它不是一个“模型直连聊天页面”的小工具，而是一个分层很清楚的 Agent 系统。

最外层是 `gateway`。它负责启动整个服务，也负责托管 HTTP 入口。以前它主要用来挂健康检查和飞书 OAuth，这次它变成了所有渠道的统一入口。

中间是 `ChannelManager`。它的职责很单纯：初始化已启用的渠道、启动它们、把 Agent 产出的出站消息分发回正确的渠道。它像一个交通调度中心，不关心业务内容，只关心消息应该去哪里。

底层是 `MessageBus`。这是皮皮虾非常重要的一层。任何渠道收到消息，都会先转成统一的 `InboundMessage`，塞进总线；Agent 处理完以后，再生成统一的 `OutboundMessage`，由渠道层取走发出去。正因为有这一层，新增一个渠道时，不需要去改 Agent 的核心思考逻辑。

再往里才是 `AgentLoop`。它负责会话、上下文、工具调用、模型推理、记忆整合。换句话说，它解决的是“怎么思考”，而不是“怎么接进来”。

这就是为什么个人微信必须实现成一个独立 channel，而不是直接往 AgentLoop 里硬塞微信逻辑。扫码登录、长轮询、媒体解密、token 缓存，都是渠道层自己的事。Agent 不应该知道这些细节，否则今天接微信，明天接别的平台，核心层就会越来越脏。

还有一个原则在这次改造中被彻底坐实了：所有 channel 必须由 `gateway` 统一启动。因为一旦渠道自己变成一个单独的 daemon，生命周期、状态、登录、日志、排障都会分裂。微信这种复杂通道，越要收口到同一个 gateway 里管理。

## 4. 这次实现参考了哪些开源项目

这次不是闭门造车，但也不是把别人的系统整个搬过来。真正有价值的，是把几个项目里各自最成熟的思路拆出来，重新拼成适合 PP-Claw 的实现。

第一个参考对象是 `nanobot`。它给我的不是“微信怎么接”，而是“多渠道怎么活得整齐”。`nanobot` 的核心启发非常直接：`gateway` 是唯一入口，`ChannelManager` 负责拉起所有启用的 channel，channel 本身是长期运行任务，而不是临时函数调用。这个思路看上去朴素，但非常重要。因为只有在这种结构下，微信这种需要长期维护状态、持续长轮询的通道，才有地方安放。

第二个参考对象是 `openclaw-weixin / nexu`。这一块的重要性，比我一开始预想的还高。原因在于它不是给你一个“聊天机器人 demo”，而是把个人微信接入拆成了一条完整的工程链路：二维码登录、登录态保存、`getupdates` 长轮询、`context_token` 绑定回复、媒体 CDN 上传下载、以及多账号并行运行。以前很多人谈“接微信”，谈到最后其实只停留在收发文本；真正把账号状态、上下文关联、媒体链路都做扎实的项目并不多。`openclaw-weixin` 给我的价值，就是它把这些难点都摊开了。

这里也要把背景说准。我们参考 `openclaw-weixin`，不是因为它“碰巧能跑”，而是因为它背后对应的 ClawBot 方向，已经不是一种完全私下摸索的个人玩法。结合你给出的微信官方说明，可以确认一个事实：微信通道这件事已经开始从“零散试验”转向“有明确叙事、有安装方式、有账号模型、有后端协议”的阶段。对工程实现来说，这个差别非常大。前者只能算 hack，后者才值得写进正式架构。

第三个参考对象其实是 `OpenClaw` 本身，但参考的是它的语义，而不是它的运行时。比如“一个 channel 可以有多个 account”，“会话隔离不应该只看 channel，还要看 peer 和 account”这一类概念，都值得保留。可我没有照搬它的 controller、plugin runtime、WS RPC 那整套外壳，因为对皮皮虾来说，那样做代价太高，而且会直接改变项目的基本形态。

所以最后的路线其实很清楚：运行时架构学 `nanobot`，个人微信协议与状态机参考 `openclaw-weixin / nexu`，账号和会话语义向 `OpenClaw` 靠齐，但最终实现仍然是 PP-Claw 自己的原生 `wechat_personal` channel。

这一步很关键，因为它决定了整个方案的耦合度。如果我当时图快，直接去“兼容 OpenClaw 插件宿主”，短期可能更省力，但后面一定会把皮皮虾拖进另一套生态。现在这样做，控制权留在自己手里，渠道层也足够内聚。

## 5. 微信接入到底是怎么实现的

真正动手的时候，我把微信这条链路拆成了五层，因为不拆开，后面一定会失控。

第一层是 `wechat_personal.go`。这是渠道主文件，对外实现的就是一个标准 channel：能 `Start`，能 `Stop`，能 `Send`，还能向 `gateway` 注册登录和状态路由。所有外界看见的入口都在这一层。比如扫码登录的 `/channels/wechat_personal/login/start` 和 `/channels/wechat_personal/login/wait`，就是它挂上去的。

第二层是 `wechat_personal_api.go`。这一层不碰业务，只封装协议。它做的事情很机械：构造请求、设置请求头、拼接 `AuthorizationType`、`Authorization`、`X-WECHAT-UIN`，然后去调 `getupdates`、`sendmessage`、`getuploadurl`、`getconfig`、`sendtyping`。这层存在的价值，是把“和微信后端说话”这件事和“渠道怎么工作”分开。否则以后只要接口字段一变，业务层和渠道层会一起被波及。

第三层是 `wechat_personal_state.go`。它负责把登录态和运行时状态落到本地。这里面保存的不只是 token，还有 `ilink_user_id`、`get_updates_buf`、`typing_ticket`、暂停时间、最近错误等信息。为什么必须落盘？因为扫码登录是一件昂贵动作，不能要求用户每次重启 gateway 都重扫一次。更现实一点说，如果一个通道需要依赖“内存不能丢”，那它根本不配进正式运行时。

第四层是 `wechat_personal_media.go`。这是整条链路里技术含量最高、也最容易把项目结构带偏的一层。它做三件事：入站媒体下载和解密，出站媒体加密和上传，最后再把上传结果包装成微信消息项。这里面最关键的是 AES-128-ECB。出站时，先读本地文件，算明文 MD5 和大小，生成 AES key，去拿上传参数，再加密上传到 CDN，最后把 CDN 引用塞回消息。入站则反过来：从 CDN 把密文拿下来，根据 `aes_key` 解密，再保存成本地临时文件。这样 Agent 层看到的永远只是“本地媒体文件路径”，而不会知道微信 CDN 的存在。

第五层是 `wechat_personal_types.go`。这层看起来最不起眼，但它其实是在把整套协议“写死”到编译期。二维码响应、长轮询响应、消息项、媒体结构、上传参数、配置响应，都在这里定义。这样做的好处是，协议字段不再散落在各个文件的 `map[string]any` 里，代码一旦写错，编译器会先帮你抓出来。

有了这五层以后，整个实现路径就顺了。

第一步是登录。CLI 调用 `gateway` 的登录接口，`gateway` 再调用微信后端的 `get_bot_qrcode` 获取二维码。这里返回的不一定是图片，有时候是一个 `liteapp.weixin.qq.com/q/...` 的链接，所以终端二维码渲染后来专门做了兼容：如果拿到的是图片就直接画，如果拿到的是链接，就把这个链接本身编码成二维码。扫码确认后，再通过 `get_qrcode_status` 轮询结果，拿到 `bot_token`、`ilink_bot_id`、`ilink_user_id` 和真实 `base_url`。这一刻开始，账号就算连上了。

第二步是把账号状态保存到本地。这里我给每个账号一个 `account_id`，比如 `wx1`。你可以把它理解成“皮皮虾内部对这个微信号的名字”。它不等于微信用户 ID，而是本地运行时用来区分多个账号实例的主键。保存之后，`gateway` 重启时就能自动恢复这个账号，不需要重新扫码。

第三步是启动长轮询。每个已登录账号都会启动自己的 monitor loop。循环逻辑很简单：读本地的 `get_updates_buf`，调用 `getupdates`，拿到新的消息列表和新的 cursor，再把 cursor 写回去。这样即使进程重启，也不会从头把历史消息重刷一遍。

第四步是处理入站消息。收到一条微信消息后，先看是不是 Bot 自己发的；再提取文本、语音转文字、图片、文件、视频等内容；如果是媒体，就先在渠道层完成下载和解密，然后把本地文件路径塞进统一的 `InboundMessage.Media`。同时，这一步还要把 `context_token` 缓存起来。因为稍后回复的时候，全靠它做关联。

第五步是把消息送进皮皮虾自己的世界。到了这里，微信就和别的渠道没什么区别了：消息进入 `MessageBus`，被 `AgentLoop` 消费；上下文按会话维度拼起来；模型推理、工具调用、子代理这些原有能力照常运行。换句话说，微信这次接入真正做对的一点，就是它尽可能晚地把自己“普通化”。在进入 Agent 之前，尽可能保留微信的特殊性；一旦进入 Agent，就尽可能表现得像一个普通渠道。

第六步是把回复发回微信。Agent 产出的 `OutboundMessage` 会被 `ChannelManager` 路由回 `wechat_personal`。这时渠道层先根据 `AccountID` 找到正确的微信账号，再根据 `ChatID` 和本地缓存取回最近的 `context_token`。如果是文本，就直接构造消息项发出去；如果带媒体，就先走上传加密链路，再把媒体消息发出去。整个发送过程都在渠道层闭环完成，Agent 完全不用知道微信是怎么发文件的。

这里还发生了一个关键的底层改动：消息模型新增了 `AccountID`。这一步不是“顺手加个字段”，而是整个多账号设计能不能成立的基础。因为只靠 `channel + chat`，一旦两个微信号都和同一个用户对话，会话和出站消息就一定串。现在升级成 `channel + account + chat` 以后，微信不但能跑，多账号也终于成了架构层面的合法能力，而不是一个脆弱特例。

说到底，这次微信接入真正做成的，不是一套“能扫二维码”的脚本，而是一条完整的通道运行时：登录能保留、消息能持续收、上下文能正确回、媒体能闭环处理、账号能并行运行。到这一步，才配说“皮皮虾已经支持个人微信收发消息了”。

## 6. 小白怎么接入：最短操作步骤

如果你不关心实现细节，只想用起来，步骤其实很短。

先在 `~/.pp-claw/pp-claw.yaml` 里打开：

```yaml
channels:
  wechat_personal:
    enabled: true
    accounts:
      wx1:
        enabled: true

gateway:
  host: 127.0.0.1
  port: 28790
```

这里我建议把 `gateway` 端口改成 `28790`，原因很现实：很多机器上的 `18790` 已经被 Docker 或旧服务占了。这个坑我自己就踩过，配置明明是对的，结果请求打到了另一套服务上，最后只剩一个 404，排起来非常恶心。

然后重新编译：

```bash
go build -o pp-claw .
```

启动 gateway：

```bash
./pp-claw gateway
```

另开一个终端，检查配置：

```bash
./pp-claw channels status
```

能看到 `wechat_personal enabled`，说明配置已经生效。

接着发起扫码登录：

```bash
./pp-claw channels wechat login --account wx1
```

正常情况下，终端会显示：

- 账号 ID
- 二维码链接
- 终端二维码
- 登录成功提示
- 微信用户 ID

登录成功以后，再看运行状态：

```bash
./pp-claw channels wechat status
```

只要看到 `running` 和 `logged-in`，就说明这条微信账号已经被皮皮虾接管了。接下来你直接用微信给它发消息，它就会收；Agent 处理完以后，也会直接从微信回给你。

这也是“微信养虾”这个说法真正成立的时刻。以前皮皮虾只是一个运行在终端或服务里的 Agent，现在它终于有了一个你每天都会打开的入口。

## 7. 最后的总结

这次改造表面上是在“给 PP-Claw 加微信”，但本质上做成的是另一件更重要的事：把皮皮虾的渠道运行时能力补齐了。扫码登录、账号状态、本地持久化、多账号并发、上下文隔离、媒体闭环，这些东西一旦在微信这条最复杂的通道上跑通，后面再接别的平台，难度就不会再是同一个量级。

更重要的是，这次实现没有为了微信去污染 Agent 核心。微信所有复杂性，都被压在了 `wechat_personal` 这个 channel 里面；而 Agent 依然只关心统一的入站消息和出站消息。这一点看起来很“工程化”，但正是这种克制，决定了皮皮虾以后还能不能继续长。

所以如果要用一句话总结这次工作，我会这么说：

**我们不是给皮皮虾临时接上了微信，而是让它真正学会了如何住进微信。**
